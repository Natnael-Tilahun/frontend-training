# 10. Tooling: what each tool does and why we use it

A frontend project is more than its framework. Around the code there is a set of tools that check it, format it, test it and build it. You'll meet the same kinds of tools in every professional project, often with the same names. This guide explains each one in this repo: **what** it is, **why** we use it, and **how** it is set up.

## The big picture

Each tool catches a different kind of problem, and each one runs as early as possible:

| Tool                    | Question it answers                          | When it runs                         | Config file                           |
| ----------------------- | -------------------------------------------- | ------------------------------------ | ------------------------------------- |
| **Prettier**            | Does the code _look_ consistent?             | Every save (VS Code)                 | `.prettierrc.json`, `.prettierignore` |
| **ESLint**              | Does the code follow our rules?              | As you type, on save, `npm run lint` | `eslint.config.mjs`                   |
| **TypeScript**          | Do the types fit together?                   | As you type, `npm run typecheck`     | `tsconfig.json` (generated by Nuxt)   |
| **Vitest**              | Does the logic give the right answers?       | `npm test`                           | `vitest.config.ts`                    |
| **Nuxt build (Vite)**   | Can the app be built for production?         | `npm run build`                      | `nuxt.config.ts`                      |
| **GitHub Actions (CI)** | Do all of the above pass on a clean machine? | Every push and pull request          | `.github/workflows/ci.yml`            |
| **EditorConfig**        | Does every editor use the same basics?       | Always, in any editor                | `.editorconfig`                       |

The rule of thumb: **the earlier a problem is caught, the cheaper it is.** A red underline while typing costs seconds. A failed CI run costs minutes. A bug found by a user costs days.

## Node, npm and `package.json`

**What:** Node.js runs JavaScript outside the browser. All our tools (Nuxt, ESLint, Vitest…) are Node programs. **npm** installs packages and runs scripts.

**Why it matters:**

- `package.json` lists the packages the project uses and the **scripts** you run. It is the first file to read in any project.
- `dependencies` are needed by the app itself (Vue, Nuxt, Zod…). `devDependencies` are only needed while developing (ESLint, Prettier, Vitest, TypeScript).
- `package-lock.json` records the **exact** version of every package. Commit it. It's why everyone (and CI) installs the same thing.
- `npm install` adds or updates packages and may change the lock file. `npm ci` installs exactly what the lock file says and never changes it. CI uses `npm ci`.
- `.nvmrc` says which Node version the project expects (22). With nvm, `nvm use` switches to it. `engines` in `package.json` says the same thing to npm.

**The scripts you'll use:**

| Script              | What it does                                                            |
| ------------------- | ----------------------------------------------------------------------- |
| `npm run dev`       | Starts the app at http://localhost:3000 with hot reload                 |
| `npm run lint`      | Runs ESLint on the whole project                                        |
| `npm run lint:fix`  | Runs ESLint and fixes what it can automatically                         |
| `npm run format`    | Runs Prettier on every file                                             |
| `npm run typecheck` | Runs the TypeScript checker on the whole project, `.vue` files included |
| `npm test`          | Runs the unit tests once (`npm run test:watch` re-runs them on save)    |
| `npm run check`     | lint + typecheck + test: **run this before every push**                 |
| `npm run build`     | Builds the production app into `.output/`                               |

`postinstall: nuxt prepare` runs after every install. It generates the `.nuxt/` folder: the types for auto-imports, the TypeScript config and the ESLint config. If your editor shows strange errors after pulling, run `npm install` (or `npx nuxt prepare`) again.

## Prettier: formatting

**What:** a code **formatter**. It rewrites the layout of your code (spaces, line breaks, quotes, commas) into one consistent style. It never changes what the code does.

**Why:**

- Nobody argues about style in code review any more. The tool decides.
- Diffs show only real changes, not someone's re-indenting.
- You stop spending attention on layout while you type.

**How it's set up:** `.prettierrc.json` holds the few choices we made:

```jsonc
{
  "semi": false, // no semicolons
  "singleQuote": true, // 'text' instead of "text"
  "printWidth": 100, // wrap lines longer than 100 characters
  "trailingComma": "all", // a comma after the last item, so adding one changes one line
}
```

`.prettierignore` lists what Prettier must not touch: generated folders (`.nuxt`, `.output`), `node_modules` and the lock file.

VS Code formats on every save because of `.vscode/settings.json` (`editor.formatOnSave` with the Prettier extension). From the terminal: `npm run format`.

## ESLint: linting

**What:** a **linter** reads your code without running it and reports patterns that are likely bugs or break the team's rules. The name comes from "lint", the fluff you pick off clothes: small things that make code worse.

**Why:** some mistakes are valid JavaScript, so neither the browser nor TypeScript complains, but they are almost always wrong:

- a variable you declared but never used (often a typo or a forgotten step)
- `any`, which switches TypeScript checking off
- a `console.log` left behind from debugging
- Vue-specific mistakes: a `v-for` without `:key`, mutating a prop, a wrong `v-model`

Here is real output from this repo for a small bad file:

```text
app/utils/demo.ts
  1:30  error    Unexpected any. Specify a different type                @typescript-eslint/no-explicit-any
  2:7   error    'unused' is assigned a value but never used             @typescript-eslint/no-unused-vars
  3:3   warning  Unexpected console statement                            no-console

✖ 3 problems (2 errors, 1 warning)
```

Each line gives the **position** (line:column), the **level**, the **message** and the **rule name**. Search the rule name to read why it exists.

- **error** fails `npm run lint` and CI. Fix it before you push.
- **warning** is reported but doesn't fail. Use it for things that are sometimes fine.
- Some rules are **auto-fixable**: `npm run lint:fix`, or save in VS Code (`source.fixAll.eslint` in `.vscode/settings.json`).

**How it's set up:** `eslint.config.mjs` uses the modern "flat config" format (one JavaScript file, ESLint 9+):

```js
import withNuxt from './.nuxt/eslint.config.mjs'

export default withNuxt({
  rules: {
    'vue/multi-word-component-names': 'off', // pages like index.vue are fine
    'vue/require-default-prop': 'off', // typed optional props are undefined by default
    'vue/html-self-closing': 'off', // formatting is Prettier's job
    '@typescript-eslint/no-explicit-any': 'error', // never silence TypeScript with any
    'no-console': ['warn', { allow: ['warn', 'error'] }],
  },
})
```

- The `@nuxt/eslint` module **generates** a recommended config for Nuxt, Vue and TypeScript in `.nuxt/`. We only add our own choices on top.
- Each rule is `'off'`, `'warn'` or `'error'`, sometimes with options.
- Turn a rule off **for the whole project** only when the team agrees, with a comment saying why.
- For a single, justified exception, disable it on one line and explain:

  ```ts
  // eslint-disable-next-line no-console -- printed on purpose in the seed script
  console.log('Seeded 12 products')
  ```

  Never disable a rule just to make the error go away.

## ESLint vs Prettier vs TypeScript

These three are the most commonly confused. Each one has a different job:

| Tool       | Looks at                | Example it catches                                             |
| ---------- | ----------------------- | -------------------------------------------------------------- |
| Prettier   | Layout only             | Inconsistent quotes, indentation, long lines                   |
| ESLint     | Patterns and team rules | Unused variable, `any`, missing `:key`, leftover `console.log` |
| TypeScript | Whether types fit       | Passing a string where a number is expected, a missing field   |

Rules of thumb:

- **Prettier formats, ESLint judges.** We turn off ESLint's style rules so the two never fight.
- **TypeScript checks types, ESLint checks habits.** Code can type-check perfectly and still have an unused variable.
- None of them prove the code is **correct**. That's what tests are for.

## TypeScript type-checking

**What:** VS Code checks types as you type, but only in the files you have open. `npm run typecheck` (Nuxt runs **vue-tsc**, TypeScript that understands `.vue` files) checks the **whole** project at once.

**Why:** if you change a type in `shared/`, a file you never opened may break. The editor won't show that; `typecheck` and CI will.

**How it's set up:** `tsconfig.json` only points at configs that Nuxt generates in `.nuxt/` (separate ones for the app, the server, `shared/` and Node). `typescript.strict: true` in `nuxt.config.ts` turns on strict mode. Don't edit the generated files. Change settings in `nuxt.config.ts`.

## Vitest: tests

**What:** a test runner. A test calls your code with some input and checks the output:

```ts
it('treats zero as out of stock', () => {
  expect(getStockLevel(0)).toBe('out')
})
```

**Why:** tests prove that logic still works after a change, without clicking through the app. They are also the best documentation of edge cases.

**What we test here:** pure logic that is easy to test and expensive to get wrong: formatting, Zod schemas, error helpers, `useSearch`, stock levels. Tests live in `tests/unit/*.test.ts`.

**How it's set up:** `vitest.config.ts` runs tests in Node and adds the `#shared` alias. These tests don't load Nuxt, so they import things explicitly (`import { ref } from 'vue'`). Component tests that need Nuxt's auto-imports would use `@nuxt/test-utils`.

## The build: Nuxt and Vite

**What:** `npm run build` turns the source into optimised files for production in `.output/`. Nuxt uses **Vite** underneath: it bundles the code, removes unused parts, and processes Tailwind CSS and TypeScript. In development, Vite serves files instantly and hot-reloads the page when you save.

**Why it's in the checks:** some problems only appear when building, such as a wrong import path in a file that the dev server never loaded.

## EditorConfig

**What:** `.editorconfig` sets the basics every editor understands: UTF-8, 2-space indentation, LF line endings, a final newline, trimmed trailing spaces.

**Why:** people use different editors and operating systems. Without it, Windows line endings or tabs can sneak in and create noisy diffs.

## VS Code setup

- `.vscode/extensions.json` recommends the extensions VS Code should offer to install: **Vue (Official)**, **Tailwind CSS IntelliSense**, **ESLint**, **Prettier** and **EditorConfig**.
- `.vscode/settings.json` makes Prettier the formatter, formats on save and runs ESLint auto-fixes on save.

Without the extensions, nothing is checked while you type, and you only find out at `npm run check` or in CI.

## Git, pull requests and CI

- `.gitignore` keeps generated and private files out of Git: `node_modules`, `.nuxt`, `.output`, `.env`.
- `.env.example` shows which environment variables exist. Copy it to `.env` for local values. `.env` is never committed, because it can hold secrets.
- `.github/pull_request_template.md` pre-fills every pull request with a checklist.
- `.github/workflows/ci.yml` is **continuous integration** (CI): on every push and pull request, GitHub starts a clean machine and runs `npm ci`, lint, typecheck, tests and build. A red ❌ on the pull request means one of them failed. Open the run to see which.

**Why CI when we can run `npm run check` locally?** Because people forget, and "it works on my machine" is not proof. CI is the same check, on a clean machine, every time. A team normally doesn't merge a pull request with a red CI.

## The libraries: why each one is in `package.json`

| Package                             | Job                                             | Why this one                                                  |
| ----------------------------------- | ----------------------------------------------- | ------------------------------------------------------------- |
| `nuxt`, `vue`, `vue-router`         | Framework, components, routing                  | File-based routing, auto-imports, data fetching built in      |
| `tailwindcss`, `@tailwindcss/vite`  | Styling with utility classes                    | No CSS files to maintain; design tokens in one place          |
| `class-variance-authority`          | Component variants (`variant="danger"`)         | Typed variants instead of hand-written class conditions       |
| `clsx`, `tailwind-merge`            | Used by `cn()` to combine classes               | Conditional classes, and later classes win over earlier ones  |
| `pinia`, `@pinia/nuxt`              | Shared state (the signed-in user)               | The official Vue store, typed, visible in Vue DevTools        |
| `zod`                               | Validation schemas and types from one source    | One rulebook for the form, the server and TypeScript          |
| `vee-validate`, `@vee-validate/zod` | Form state: values, errors, touched, submitting | Works with Zod schemas directly                               |
| `lucide-vue-next`                   | Icons                                           | Consistent set; each icon is imported, so only used ones ship |
| `@fontsource-variable/inter`        | The Inter font                                  | Bundled with the app: no external font request                |

## Daily workflow

1. Pull the latest code, and run `npm install` if `package.json` changed.
2. `npm run dev` and work. Prettier and ESLint fix what they can on every save; fix the red underlines as they appear.
3. Before you push: `npm run check`. Fix every error.
4. Open a pull request, fill in the template, and wait for a green CI.

## Common problems

| Symptom                                          | Cause and fix                                                                                               |
| ------------------------------------------------ | ----------------------------------------------------------------------------------------------------------- |
| Saving doesn't format the file                   | Prettier extension missing, or another formatter is the default. Install it; check `.vscode/settings.json`. |
| `Cannot find module './.nuxt/eslint.config.mjs'` | `.nuxt/` isn't generated yet. Run `npm install` or `npx nuxt prepare`.                                      |
| Auto-imported names (`ref`, `useFetch`) are red  | Same: run `npx nuxt prepare`, then "Restart Vue Server" from the VS Code command palette.                   |
| Lint passes locally but fails in CI              | You didn't run it on the whole project, or the lock file changed. Run `npm ci && npm run check`.            |
| `npm ci` fails                                   | `package.json` and `package-lock.json` disagree. Run `npm install` and commit the lock file.                |
